__Level 1: TCP Plumbing and Message Framing__
Main resource referred to: geeksforgeeks.com [Computer Networking, Client-Server Model (got my server and client C++ boiler template code from here, I modified it to meet the requirements)]

Level 1 focuses on setting up a TCP client and server. This is done using sockets, which are used for communication between a client and a server over a network. In a client-server model, the client sends a request to the server, which processes it and sends back a response to the client. The basic flow of communication looks something like this:

Server: Create Socket -> Bind -> Listen -> Accept -> Receive -> Send

Client: Create Socket -> Connect -> Send -> Receive (taken from geeksforgeeks.com)

We will be using various socket functions to implement this. Since this is a Windows socket program, I included winsock2.h and ws2tcpip.h as they contain the core socket functions and IP extensions. If this was done using a Linux kernel instead, they could be avoided as these socket functions are built into the kernel.
TCP is a byte stream protocol, so data arrives as an unsegmented continuous flow of bytes. What this means is that without proper framing, the message may end up jumbled as TCP doesn't have set message boundaries. To tackle this problem, I'm using TLV framing (Type, Length, Value/Payload). This system of framing is used in modern day network protocols like TCP/IP. Basically, a message is composed of 3 components: 1 byte specifies the type of the message (whether it is a chat message or a key exchange etc (we will see this properly in later levels), the next 4 bytes specify the length of the payload, and then the n byte payload follows. Within the program, the recv() function works in such a way that it takes each of these components into consideration by reading the headers first and then the payload itself to ensure that the messages don't splice into each other. In this codebase, I've used 0x01 for chat message, 0x02 for key exchange message and 0x03 for mac value message.

To prove that this works for multiple messages of different sizing, 4 different messages have been hardcoded and sent from between the sockets to show that they arrive in the correct order (TCP) without being merged or spliced into (TLV). Further explanations are written into the code. The setting up of raw client server socket was the easier part as there were direct resources available online. The framing was harder so my learning process for this was using AI resources available online for the coding part, especially syntax since the logic is pretty straightforward. __Level 2: Diffie-Hellman Key Exchange__

I'm implementing regular Diffie-Hellman right now. I was running into some issues with OpenSSL, unfortunately, and implementation of ECDH without an OpenSSL or libsodium library is pretty hard. I did read up on both though. So, DH algorithm relies on exponents and logarithms. It is asymmetric cryptography with symmetric key. This means that for encryption and decryption, the same secret key will be used but both parties have a private key for computation and a public key that is shared. So basically, how DH works afaik is that there is a base G generated and a prime number P. These are publicly shared and each party has a private number say a and b. Each party will generate G^a mod P and G^b mod P and then share this value to each other as A and B. Then using their private keys on this, they will arrive at a shared key ie A^b mod P=B^a mod P. In ECDH, G and P are replaced by E, the elliptic curve equation coefficients and G which is a point on the curve. This drastically shortens the number of bits or the size of the key to be used which is its major advantage over DH. For the implementation of DH, I've made use of modular arithmetic.

__Level 3: Key Derivation__

To make everything more secure, we take the shared secret key value we computed from Level 2 and put it through a key derivation function to generate an encryption key to scramble our message and a mac key to authenticate who the message came from as well. Ok so I did look through HKDF and its implementation in code online, but I wasn't really able to understand the implementation, so I stuck to a mixing algorithm. The function I implemented, takes the shared secret key, applies golden ratio constant additions to break any patterns that may occur, non-linear bitwise XOR shifts to make sure that if there is even a slight modification that comes up it cascades into a very evident error (flipping even one bit builds upto maybe half the bits in the final completely changing output - diffusion principle), and large prime multiplications for non linearity. We also don't use same input to generate both mac and encryption keys so that they are independent of each other and even if one is compromised the other can be secure.
Major challenge was choosing the KDF algorithm and trying to fulfill the requirements using different operations to make the keys secure.

__Level 4: Handshake Confirmation__

This deals with Man in the Middle attacks and one thing that TLS does to safeguard against this, is the handshake confirmation which I will be implementing. Handshake confirmation forces both sides to prove that they successfully completed the handshake and arrived at the exact same shared keys before any actual chat messages are sent. If anything was tampered with in transit, the mac check fails, and the protocol aborts immediately. So, in this code, we collect every handshake message that has been sent so far (aka the client and server's public keys) and then put them into a single string buffer called the transcript. If even a bit is changed in either of the public keys shared by an attacker, the transcript of client and server would then be different. Both the client and server run a keyed function over this transcript using their derived mac_key. Because both sides have the exact same public keys and the exact same mac_key, they should generate the exact same value (transcript=client +server public keys so they should be equal). They send this value to each other and if received value matches what they locally computed, it means handshake was successfully and authentication takes place in this manner. The mac value is computed using FNV-1a hashing algorithm found online where the transcript is condensed and xor-mixed and shifted with the mac_key. So, an attacker who didn't take part in DH algorithm can't know the mac_key either so accurate mac value would be nearly impossible for them to compute. In the implementation video I tampered with the client's public key by flipping its first bit to show that the handshake confirmation protocol works.

__Level 5: Encrypted, Authenticated Messaging__

Level 5 was my favourite to work on. They deal with ciphers which basically make the messages you send more secure because they ensure that even if someone intercepts your message, they can't make sense of it without a key. Ciphers are used to scramble these messages basically they display what appears to be garbage to these attackers instead of plaintext. Think of them like a puzzle that can only be solved with a key that would not be available to anyone outside the connection. This is what makes this whole chat confidential. So far, we have mostly only secured and authenticated the connection itself, but we haven't done anything to the messages itself. That changes in this level.  
To encrypt the message (plaintext to cipher) the function combines the enc_key with the message's rolling sequence number (comes up later as part of the bonus asw) to initialize a random state. It runs a mixer to generate a unique keystream byte for every character and xors the plaintext with the keystream to produce ciphertext. Because XOR is symmetric, calling the exact same function on the receiving end with the same key and sequence number reverses the process and extracts the original plaintext. To detect messages that may be replayed, the code has two counters on both sides that are incremented by 1 with every message sent or received. As mentioned in the README, we also authenticated the messages with MAC. This is because if there is a case where an attacker corrupts your message, then that should also be detected. Authentication with MAC ensures the integrity of the message. So, for doing this, we compute the mac value of the rolling sequence number and the cipher using mac_key. This mac value is attached along with the message so our framing needs to be slightly modified here (basically our payload is subdivided into 8 bytes for seq_num, 8 bytes for mac value and n bytes for the ciphertext). Anyway, mac values are computed locally and then compared to check for tampering. 

__Level 6: The Chat Application__

An important concept being used in this level is concurrency. In the previous levels, we were hardcoding messages to show implementation but, in this level, we have to simultaneously send and receive messages, so we used threads. The main thread waits for us to send the message and type it in, whereas the background worker thread runs quietly listening for any messages from the client. Since we have two threads running at the same time, we need to manage them properly using functions from the atomic library (y(function running()). If the connection drops or someone types exit or if a security alert triggers, the code flips running to false. Both threads immediately see this flag change, break out of their loops, and safely close the sockets without crashing or deadlocking. The background thread has to stop first. As for how the threads themselves work, the main thread reads lines from the keyboard using getline and when we type exit the app shuts down. This thread mostly deals with user interaction aka the client, so it mostly encrypts data, binds it with necesarry details like seq_num and mac key and then sends it over the network to server. The background worker thread receives this message, extracts the sequence number, mac, and ciphertext. Then verifies these values with its own computed values to check its confidentiality and integrity making use of our previous level's implementations and then decrypts the message, following which it is printed. this mostly runs on server.
